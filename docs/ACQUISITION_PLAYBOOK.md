# 获客数据从哪来：买、导、还是等

> 回答一个很实际的问题：**获客数据到底是买，还是有别的路？**
> 结论：买是行业常规做法，但买的是**数据订阅**，不是「一份名单」；而且买来的名单
> 必须过三道工序（登记来源 → 逐条评分 → 人工审批）才能发出去。
> 本文只讲「数据怎么进系统」，合规门禁的细节见 [`OUTREACH_COMPLIANCE.md`](OUTREACH_COMPLIANCE.md)。
> **只做中国起运**的采购决策（Panjiva 怎么开通、国内数据商怎么选、合同八条、中国海关数据为什么没有邮箱）见
> [`DATA_SOURCING_CN.md`](DATA_SOURCING_CN.md)。

---

## 一、先分清三件被混为一谈的事

| 说法 | 实际是什么 | 对应代码 |
|---|---|---|
| 「买客」 | 订阅一个**数据源**（按国别/品类/条数计费），你拿到的是可查询的记录 | `ProspectingSource` |
| 「买名单」 | 一次性交付的 CSV/Excel 导出，通常是上面那个订阅的导出物 | `POST /api/v1/prospects/import` |
| 「等客」 | 官网、内容、询价表单带来的主动询价 | 走主流程，不走获客模块 |

这三条**不是替代关系**。真实货代公司三条都在跑：inbound 转化最高但最慢，
订阅数据负责「找到还没听说过你的人」，转介绍负责「找到信任已经存在的人」。

## 二、中国大陆真实可得的六类数据源

### 免费能拿到什么，拿不到什么

这是本节最要紧的一段，因为它决定了「先不花钱能不能开始」：

| 免费源 | 能给你 | 给不了你 |
|---|---|---|
| **ImportYeti** | **美国进口商（consignee）与出口商（shipper）的真实公司名**、提单记录 | 中国出口侧数据；实时性；完整联系方式 |
| **UN Comtrade** | 按 HS 6 位的国别贸易额、量、月度/年度趋势 | **任何企业名**——它只有汇总 |
| **中国海关总署统计** | 中国进出口的 HS × 国别汇总 | **任何企业名**——同上 |

**关键结论：能免费看到「企业名」的只有少数国家，美国是唯一规模化的免费源。**
原因是美国海关的提单记录可依《信息自由法案》(FOIA) 申请公开，而中国大陆的报关数据
不对普通企业开放。所以：

- 想找**海外买家**（谁在从中国进口）→ **ImportYeti 免费就够起步**，而且这条最对口货代。
- 想找**中国出口商**（谁在出货、走哪条航线）→ 只能买持牌数据商，没有免费替代。

### 「是每天更新吗」——这句话要拆开问

- **按国家差异极大**，不是一个统一频率：美国、巴基斯坦这类较快（周级），
  多数国家滞后 1–2 个月；行业普遍做法是原始提单每月更新两次（月中、月末）。
- 免费源通常**再慢一档**（月级），且出口数据、墨西哥货物、清关数据的滞后可能长达数月。
- 要区分**抓取频率**和**数据生成频率**：平台每天去抓，不等于源数据是昨天的。
  问供应商时必须问「最近一条记录的日期是多少」，而不是「你们每天更新吗」。
- 美国还有个坑：企业可以向海关申请**「电子舱单保密」**，把自己的进口记录设为私密——
  所以「查不到」不等于「没有进口」。

**系统里怎么落地**：导入时传 `data_as_of`（供应商声称的数据截止日），
`GET /api/v1/prospects/{id}/evidence` 会返回它和 `age_days`。
日期缺失、无法解析、或在未来，一律返回 `null`——**不返回 0**，
因为「不知道多旧」和「今天刚更新」是两件事。

## 三、三条进入系统的路径（都已经在代码里）

### 路径 A：导入一份名单（最常见）

数据商九成情况下给你的是一个 CSV 导出，不是一个 REST API。所以导入路径是主路径：

```bash
curl -X POST http://localhost:8100/api/v1/prospects/import \
  -H 'Content-Type: application/json' \
  -H 'X-Demo-Tenant: tenant-demo' -H 'X-Demo-User: u1' \
  -d '{
    "source": "tradesns",
    "data_origin": "vendor_contract_2026",
    "contract_ref": "TS-2026-0142",
    "data_as_of": "2026-09-30",
    "format": "csv",
    "default_lane": "Shanghai -> Los Angeles",
    "content": "公司,国家,行业,货量,邮箱\n铁杉贸易,德国,机械,260,ops@tsuga.test\n"
  }'
```

- `source` 与 `data_origin` **必填**。一份说不出从哪来的名单，正是那份不能合法发信的名单，
  所以在门口就被拒（`422`），而不是先存下来以后再想。
- 表头会做**映射**：`Est Volume TEU` / `teu` / `货量` / `annual teu` 都是同一个字段。
  不做映射的话货量会静默导入成 `None`，然后被打成「低货量线索」——
  一个看起来像数据问题、实际是映射问题的错误答案。
- 去重用**两个键**：
  - `(source, source_ref)` —— 同一份导出重导是空操作；
  - `(归一化公司名, 邮箱)` —— 从两家数据商买到同一家货主，是同一条线索。
    同名但邮箱不同视为**第二个联系人**，保留。
- 拒收会分类计数：`missing_company` / `bad_email` / `duplicate`。
  货量解析失败**不拒收**（那是解析瑕疵，不是这家公司不存在）。

### 路径 B：接入有 REST 接口的数据商

`ProspectingSource` 是可插拔接口，`search(lane, industry, limit)`。
`LicensedVendorProspectingSource` 是骨架：端点、鉴权、字段映射都是合同特定的，
实现它只需要把供应商返回的 JSON 归一化成 `ProspectRecord`。

**为什么骨架不假装实现**：写一个假的 vendor adapter 比不写更糟——
它会让人以为「接好了」，而真实合同一到，字段名、鉴权方式、分页规则全都不一样。

### 路径 C：Inbound（不走获客模块）

客户自己发询价进来，直接进主流程（`POST /api/v1/inbound/email`）。
这条路**不需要任何名单**，也是唯一不需要证明「合法处理依据」的路——因为是对方主动来的。

## 四、导入之后必须做的一件事：逐条评分

导入的 `status='imported'`、`score=0`。**导入不等于合格**。

```bash
curl -X POST http://localhost:8100/api/v1/prospects/prs_xxx/score -H 'X-Demo-Tenant: tenant-demo'
# {"verdict":"qualified","score":90.0,...}  或  {"verdict":"excluded",...}
```

这一步把「一份名单」变成「一组线索」。三种结果：

| Agent 判定 | 落库结果 | 后续 |
|---|---|---|
| `qualified`（≥55 分） | `status=discovered`，写入分数与理由 | 可富化 → 可进外联队列（还要过 70 分下限） |
| `excluded` | `status=rejected`，`score=0`，写入拒绝理由 | 不再进入外联，但保留在库里可复查 |
| 没给判定 | **抛 `agent_returned_no_verdict`** | 不写 0 分——「模型没回答」和「模型说它不行」是两件事 |

**为什么这条链是安全的**：未评分的行 `score=0`，发送时的评分下限（默认 70）直接拒。
所以「买了名单 → 群发」这条最危险的路，在代码层面走不通：
必须逐条评分、逐条审批、还要过频率上限。

## 五、买名单的四个坑，和我们的对策

| 坑 | 现实后果 | 对策（代码位置） |
|---|---|---|
| **来源不明** | 无法证明合法处理依据，一封邮件就可能违法 | 导入强制 `source` + `data_origin` + `contract_ref`（`schemas.ProspectImportIn`） |
| **重复** | 同一家公司从三家供应商买来三次，被三家货代同时轰炸 | 双键去重（`import_prospects`） |
| **质量差 / 过期** | 联系人离职、公司注销、货量是估算值 | 逐条评分 + 发送分数下限 + `est_volume_teu` 明确标为「预估」 |
| **群发冲动** | 一次导入 5000 条，一次发完 | 人工审批 + 频率上限（30 天 2 次）+ 评分下限 |

## 六、明确不做的事

- **不做爬虫**。阿里国际站、企查查等平台的 ToS 普遍禁止抓取；爬来的数据也证明不了
  合法处理依据。省下的钱不够付一次投诉的成本。
- **不做「绕过登录」的采集**。同上，且技术上不可持续（反爬升级 = 数据断供）。
- **不伪造可核验的来源**。合成数据就是合成数据，`/evidence` 会明确标 `synthetic`。
  一个点开是 404 的「来源链接」比诚实地说「无法核验」更糟，因为它会通过评审而不被检查。

## 七、已知缺口（诚实清单）

| 缺口 | 影响 | 下一步 |
|---|---|---|
| 跨供应商实体解析只做了**归一化**，没做真正的 entity resolution | 「Meridian Trading Co., Ltd」与「Meridian Trading (Shanghai)」会被当成两家 | 引入公司名相似度 + 域名匹配；或接入一个工商信息 API 做主体对齐 |
| 没有字段级的来源追溯 | 只知道整行来自哪个供应商，不知道「货量」这个字段是不是估算 | 供应商导出时带上 `field_confidence`，或按供应商维护字段可信度表 |
| 名单新鲜度**可见但不参与排序** | `age_days` 已经返回，但两年前导入的线索和上周导入的在列表里顺序一样 | 把 `age_days` 做成排序衰减因子；超过阈值时在界面上标「过期」 |
| 没有 inbound 归因 | 不知道哪个渠道带来的询价最多 | 询价单上加 `acquisition_channel`，统计各渠道转化率 |

## 八、今天就能做的三件事

1. **拿一份真实导出跑一次导入**（哪怕是 20 行），看拒收原因分布——
   如果 `duplicate` 占比很高，说明供应商之间高度重叠，不值得买第二家。
2. **给每条线索跑一次评分**，看 `excluded` 的理由是否集中在某个行业——
   那是选品问题，不是线索质量问题，该改的是目标客户画像。
3. **只对评分 ≥70 且人工审批过的线索发第一批**，把回复率记下来。
   获客的瓶颈从来不是名单数量，是「发出去的东西值不值得回」。
