# 演示界面：评估、优化方案与页面设计

> 本文回答三个问题：**现有界面缺什么**（评估）、**为什么这么补**（方案）、**每个页面怎么用**（设计）。
> 落点是一组只读演示页，不进入业务 API 面，仅在 `ENVIRONMENT != production` 时挂载。

---

## 一、评估结论

| 维度 | 结论 | 依据 |
|---|---|---|
| 后端能力完整性 | **高**。v2.0 的图编排、SOP 检索、工具调用、度量都已完成并有测试 | 298 passed，`NODES` 11 节点、5 个只读工具、`/metrics/agent` 双 block |
| 界面完整性 | **低**。四个能力面里只有一个有界面 | 补前只有 `overview.html`（v1 十阶段）+ `prospecting.html` |
| 结构合理性 | **中**。页面能跑，但彼此不可达、令牌复制而非共享 | 两个页面各内联一份 ~130 行 CSS 副本；无导航 |
| 可验证性 | **低**。只有静态断言，没有任何东西证明 JS 会执行 | 补前 `test_demo_contract.py` 只解析 HTML 文本 |
| 风格一致性 | **高**。已有一套克制的中性配色与紧凑排版 | `--bg:#F7F6F3` / `--amber:#BA7517` / `--teal:#0F6E56` |

**一句话结论：后端已经长出了 v2.0 的四个能力面，但界面上只看得到一个 v1 的流程条。**
这不是「页面不够漂亮」的问题，是**能力不可见**的问题——面试或投标时，对方只能相信他看见的东西。

---

## 二、完整性问题：具体缺什么

### 2.1 三个能力面在界面上完全不存在

| 后端能力 | 补前有无界面 | 后果 |
|---|---|---|
| LangGraph 11 节点条件图 | ❌ | 只能靠 curl 证明「有分支」，讲不清「为什么是图不是循环」 |
| SOP 检索 + 引用 + **拒答** | ❌ | 拒答是 RAG 最重要的能力，却没有地方能演一次「它敢说不知道」 |
| 只读工具调用轨迹 | ❌ | 「模型能不能乱查数据」这个问题只能口头回答 |
| 运行延迟 / 成本度量 | ❌ | 字段刚被读回来，但没人看得见 |

### 2.2 「写进去没人读」的字段

`agent_runs.latency_ms` / `prompt_tokens` / `completion_tokens` / `cost_usd` 这四个字段从 v2.0 起就在写，
但直到 N5 才有第一个读者（`services/metrics.py`）。字段写进去而没有读者，等于没有可观测性——
**这个仓库已经为这个模式付过一次代价**：`elapsed_ms` 只写不读，导致「节点耗时」这张卡片长期是空的。

### 2.3 首页不是一个入口，是一个表单

`/demo/` 原本直接渲染「提交一封询价邮件」的表单。它演示的是**一个接口**，
而项目有四个可独立验证的能力面。访客打开首页，看不到项目边界在哪里。

---

## 三、结构合理性问题

### 3.1 令牌复制而不是共享

`overview.html` 与 `prospecting.html` 各自内联了一份配色与排版令牌（约 130 行，逐字相同）。
加第三、第四个页面就会变成四份副本；改一次主色要改四处，且没有任何测试会告诉你漏了一处。

### 3.2 页面之间不可达

没有顶栏，也没有互相的链接。演示时必须记住四个 URL，中途切页面靠手打地址。
更实际的问题是：**讲完图编排，没法顺手跳到知识台**——演示的叙事被打断了。

### 3.3 契约只守了一半

`tests/test_demo_contract.py` 断言页面里的阶段元数据与 `orchestrator.STAGES` **逐字一致**，
这很好。但 v2.0 新增的 `graph/builder.NODES`（11 个节点）**没有任何契约守卫**——
页面里写死 11 个节点名，后端改一个名字，页面会安静地渲染出一个错误的图。

---

## 四、可验证性：这是最严重的一条

`test_demo_contract.py` 是**静态解析**。它能证明页面里出现了字符串 `hitl_review`、
出现了 `answered` 分支；它**不能**证明页面渲染得出来。

这个仓库刚吃过一次一模一样的亏：**259 个测试全绿，同时第一次真实请求返回 500**
（`no such column: agent_runs.prompt_tokens`——本地库是旧 `create_all` 建的，迁移 0002 的四列从没到过）。
测试全绿与服务能跑是两件事；同理，**HTML 里有字符串与页面能点开是两件事**。

所以这次补页面，必须同时补一层**运行时**证据。

---

## 五、优化方案

### 5.1 三条原则

1. **每个 v2.0 能力必须有一个能「看见」它的页面。**
   可观测性不是接口存在，是有人读。
2. **共享外壳，但不重写已有页面。**
   新建 `theme.css` 承载令牌与通用组件；`overview.html` / `prospecting.html` 只注入顶栏，
   不动它们内联的令牌副本——那两个文件有契约测试守着，且没人要求改它们，
   机械重写只会产生巨大无意义 diff。
3. **每个新页面的断言必须能失败。**
   静态契约（节点名 / 元素 id / 端点名）+ 运行时冒烟（真在 jsdom 里点按钮、读 DOM）两层。

### 5.2 做什么 / 不做什么

| 做 | 不做 | 理由 |
|---|---|---|
| 新增 2 个能力页 + 重写首页 | 不引入前端框架 | 演示页是**证据**不是产品；构建步骤会让「clone 下来就能看」失效 |
| 抽 `theme.css` | 不把 overview/prospecting 的令牌搬过去 | 见原则 2 |
| 新增 2 个只读端点（询价列表、语料清单） | 不为页面新增任何写接口 | 页面只读，写操作全部走已有的业务接口 |
| jsdom 运行时冒烟 | 不上 Playwright / 浏览器 | jsdom 够用，且 `tests/` 里能 skip-with-reason |

### 5.3 页面地图

```
/demo/                    首页 —— 四张入口卡，每张写明前置条件
├── overview.html         业务闭环（v1，10 阶段线性）
├── graph.html            图编排控制台（v2，11 节点条件图）   ← 新增
├── knowledge.html        知识台（SOP / 工具 / 度量）          ← 新增
└── prospecting.html      主动获客与合规（v1）
```

首页同时回答「四个页面是什么关系」：**一条主链路 + 三个可单独验证的能力面**。

## 六、页面设计

### 6.1 共享外壳 `theme.css`（188 行）

| 层 | 内容 |
|---|---|
| 令牌 | 与 overview 完全相同的配色：`--bg:#F7F6F3` `--ink:#1F1E1C` `--amber:#BA7517` `--teal:#0F6E56` `--red:#A32D2D` |
| 骨架 | `.topnav`（含 `.brand` / `.on` / `.env`）、`.wrap`（max-width 1320）、`.card` |
| 组件 | `.step` / `.srow`（节点）、`.badge`（状态）、`.cite`（引用）、`.score`（分数条）、`.bars/.brow/.fill`（延迟条）、`.note`（plain/info/warn）、`.gatebox`（闸门）、`.metrics/.m`（度量砖）、`.kbd` |

设计取向：**中性底 + 一个强调色**。琥珀色只用于「需要人动手的地方」（主按钮、闸门），
青绿色只用于「已经安全的地方」（放行、成功），红色只用于失败与拒绝。颜色承载语义，不承载装饰。

### 6.2 `/demo/index.html` — 首页（108 行）

**用途**：给访客一个 30 秒内能看懂的项目边界，并且每张卡都告诉他「点进去需要先准备什么」。

**功能区**

| 区 | 内容 |
|---|---|
| 顶栏 | 五个页面互链，当前页高亮；右侧标 `tenant-demo · dev auth` |
| 四张入口卡 | 编号 01–04，各带一行 `.tag`（能力类别）、标题、两行说明、进入按钮、`.need` 前置条件 |
| 「第一次跑？」卡 | 三步命令 + 一条提示：启动时会校验 schema 是否在 head，不在就拒绝启动 |
| 页脚 | 一句边界声明：金额/权限/状态/审批/发送由确定性代码控制，`AUTH_MODE=dev` 不可用于生产 |

**交互流程**：纯导航，无 JS。

**衔接**：`.need` 里的前置条件对应真实端点——「页面内可一键创建」意味着该页自己会调
`POST /api/v1/inquiries`；「页面内可一键灌入」意味着调 `POST /api/v1/knowledge/seed`。
访客不会遇到「点进去一片空白且不知道原因」。

### 6.3 `/demo/graph.html` — 图编排控制台（482 行）

**用途**：证明「这是一张有条件的图，不是一个 for 循环」。
核心不是把流程画出来，而是**让它在该停的地方停下，再从停下的地方续跑**。

**功能区**

| 区 | 位置 | 内容 |
|---|---|---|
| 控制条 | 顶部 | 询价单下拉（`GET /inquiries?limit=30`）、船名、**合成报价开关（默认关）**、运行按钮 |
| 节点轨道 `.rail` | 全宽 | 11 个节点按 `NODES` 顺序排列，`hitl_review` / `quote_send` 标为闸门；按状态着色 |
| 执行轨迹 | 左主栏 | 每个执行过的节点一行：序号、节点名、`status`、`detail`、耗时 |
| 闸门面板 `.gatebox` | 轨迹下方 | 三种形态之一，见下 |
| 状态机语义 | 左栏 | 四个条件分支逐条列出；一段 warn 说明「本页没有一键直通按钮」 |
| 运行状态 | 右栏 | `run_id`、状态、停止原因、续跑入口 |
| 节点耗时 | 右栏 | 每节点一条横条，宽度按最大值归一 |
| 两套编排，一个业务 | 右栏 | 说明 overview（10 阶段线性）与本页（11 节点条件图）共用同一批服务层函数 |

**交互流程（三条真实路径）**

```
① 正常推进到闸门
   选询价 → 运行 → understand → … → optimize → hitl_review
   → status=waiting_approval，闸门面板出现「批准 / 驳回」
   → 批准 → POST /quotes/{id}/review → POST /graph/resume → quote_send → booking → vessel_tracking

② 缺字段
   understand 发现缺 ETD → status=waiting_clarification
   → 闸门面板变成「补 ETD」输入框 → PATCH 询价 → resume → 继续

③ 报价不足
   supplier_quotes 只有 1 条 → 停在 END，`stop_reason=supplier_quotes:insufficient_quotes`
   → 闸门面板变成「录入供应商报价」表单（供应商 / 邮箱 / 海运费 / 附加费）
   → POST /rfqs/{id}/supplier-quotes → resume → optimize → hitl_review
```

三种形态共用同一个 `.gatebox` 容器，页面按 `status` 与 `pending` 决定渲染哪一个。
**没有自动审批路径**：合成报价复选框默认不勾，且作为 `allow_synthetic_quotes` 显式传参——
不读环境变量，不会被误开。

**刷新不丢**：`loadLastRun()` 从 `/graph/status/{id}` 读持久化游标，
刷新页面后仍能看到上次停在哪、还能继续点「批准」。

**衔接**：本页只调用已有的 `/graph/run`、`/graph/resume`、`/graph/status/{id}`、
`/quotes/{id}/review`、`/rfqs/{id}/supplier-quotes`。新增的唯一端点是
`GET /api/v1/inquiries`——一个只读的下拉框数据源，`limit` 夹在 1..100，支持按 `status` 过滤。

### 6.4 `/demo/knowledge.html` — 知识台（390 行）

**用途**：证明 RAG 不只是「能答」，而是**有引用、有阈值、敢拒答**。
拒答在这里是一等结果，不是错误。

**功能区**

| 区 | 内容 |
|---|---|
| 顶栏 | 三个页签：SOP 问答 / 工具调用 / 运行度量 |
| 主栏（随页签切换） | 见下 |
| 右栏 · 语料状态 | `GET /knowledge/documents` → 「2 篇 / 40 片段」；空语料时提示去灌 |
| 右栏 · 为什么「拒答」是功能 | 域外门逻辑：领域词覆盖率低于 35% 直接返回空 |
| 右栏 · 分数怎么来的 | BM25 / 余弦 / RRF / 覆盖率四个信号的权重说明 |

**三个页签**

| 页签 | 内容 | 交互 |
|---|---|---|
| SOP 问答 | 输入框 + 4 个示例 chip（3 个能答、1 个必拒） | 提问 → 答案 + 引用；点「看检索明细」→ 重新查 `/knowledge/search` 展开四条信号 |
| 工具调用 | 问题输入 + 工具轨迹 | 每次调用渲染一行：工具名、参数、结果、**被拒绝的调用标红** |
| 运行度量 | 5 块度量砖 + 每节点 p95 横条 | 读 `/metrics/agent?days=7` |

**关键交互细节**

- **拒答的措辞**：当 `answered=false` 时，页面明确写「这是正确结果」，并给出阈值推理
  （最高分多少、阈值多少、差在哪）。同时**清空上一次的检索命中**——
  留着上一次的命中会让「拒答」看起来像「查到了但不敢说」。
- **成本显示 `null` 不显示 `0`**：没有运行上报 usage 时，页面印 `null` 并解释原因。
  印 `0` 等于宣称「这次运行零成本」，是假数据。
- **分数可追溯**：每个分数都能点开看四个分量的实际值，而不是给一个无法质疑的数字。

**衔接**：`/knowledge/ask`、`/knowledge/search`、`/knowledge/seed`、`/knowledge/documents`（新增只读）、
`/tools/ask`、`/metrics/agent`。全部只读，唯一写操作是「一键灌语料」这个显式的演示动作。

## 七、可落地性：怎么证明它没坏

| 层 | 文件 | 守什么 | 能失败吗 |
|---|---|---|---|
| 静态契约 | `tests/test_demo_pages.py`（25 项） | 节点名与 `NODES` 逐字一致、4 个入口卡、`.need` 恰好 4 个、元素 id 全部可解析、端点名出现 | ✅ 改一个节点名即红 |
| 运行时冒烟 | `scripts/page_smoke.js`（28 项检查） | jsdom 里真执行内联 JS：桩掉 `fetch`、点真按钮、读真 DOM | ✅ 页面脚本抛错即红 |
| 运行时入口 | `tests/test_page_runtime.py` | 工具链是否存在；不存在则 **skip with reason** | ✅ 两页合并一次调用，单页 ≥12 项检查否则判空转 |

冒烟实测（一次进程跑两页，14.9s）：

```
graph      13 项  轨道 11 节点 / 轨迹 7 行 / 耗时 7 条 / waiting_approval
                  / 闸门无直通按钮 / 批准后 completed 10 行 / review+resume 都被调用
knowledge  15 项  语料 2 篇 40 片段 / 4 个示例 chip / 引用渲染 / 四信号可见
                  / 拒答写明「这是正确结果」/ 旧命中被清空 / 2 步工具含 1 步被拒
                  / 5 块度量砖 / null 成本有解释 / 2 条 p95 横条
```

**为什么运行时检查是 optional 的**：CI 只装 Python。node + jsdom 在的地方跑，
不在的地方 **skip 并说明原因**——一个说明理由的 skip 是诚实的；一个什么都没执行的绿勾不是。

## 八、仍然存在的问题

| 项 | 性质 | 影响 |
|---|---|---|
| 三个页面各自写模板字符串渲染 | 无组件化 | 新增页面仍会复制渲染逻辑；演示页数量到 6+ 时应抽公共渲染函数 |
| 冒烟只覆盖 graph / knowledge | overview / prospecting 无运行时检查 | 那两个页面有契约测试，但没有「点得动」的证据 |
| 无移动端适配测试 | 只有 CSS 断点 | 演示通常在桌面投影，暂可接受 |
| `theme.css` 与两个老页面的令牌副本并存 | 技术债 | 改主色需改三处；应在下次动那两个页面时一并收口 |
