# 获客推进路线：从「有一份名单」到「有人回信」

> 这份文档回答的是**顺序问题**，不是数据源问题。
> 数据源在哪买、多少钱、合同怎么写，见 `docs/ACQUISITION_PLAYBOOK.md` 和 `docs/DATA_SOURCING_CN.md`。
> 合规闸门怎么落，见 `docs/OUTREACH_COMPLIANCE.md`。

## 〇、一句话结论

**获客的第一步不是「拿到名单」，是「确认这份名单里有人能被合法地发到」。**

这个区别决定了钱该怎么花：

- 你花钱买到的，几乎总是**公司名 + 交易记录**，不是**邮箱**。
- 中国海关数据、Panjiva、各国提单，**全都没有邮箱**（`DATA_SOURCING_CN.md` 第五节）。
- 所以「买名单」买到的是**候选池**，把它变成客户还差一步：补联系方式。
- **这一步没有免费午餐**，也没有数据商替你做完。它要么花人工，要么花工具钱。

想明白这件事，剩下的顺序就自动出来了：先用免费源把「发现 → 补联系方式 → 打分 → 触达」这条管道跑通，**用回复率证明 ICP 对了**，再决定买哪份付费数据。反过来做——先买数据再想怎么用——就是最常见的几十万打水漂。

---

## 一、漏斗的真实形状

```
① 发现公司      ② 补联系方式      ③ 打分      ④ 触达      ⑤ 回复      ⑥ 成交
   免费可覆盖        没有免费午餐      自己做       自己做       只能实测     靠前五步
```

每一步的失败方式不一样，所以要分开度量：

| 环节 | 典型失败 | 你怎么知道它失败了 |
|---|---|---|
| ① 发现 | 名录选错行业/国家 | 抓 200 家，可发信比例 < 10% |
| ② 补联系方式 | 只有公司名，没有收件人 | `contact_gaps.emailable = 0` |
| ③ 打分 | ICP 写错，把同行当客户 | 高分名单里出现竞争对手 |
| ④ 触达 | 送达率低、被投诉 | 退信率 > 5%，或收到 opt-out |
| ⑤ 回复 | 话术不对 | 发了 100 封，回复 < 3 封 |

**这五格里，只有 ① 可以花钱加速。②③④⑤ 花钱都买不到。**

## 二、免费和付费怎么「打通」

不是「免费先用、付费后用」，是**同一个管道挂多个源**。这是代码里已经实现的结构：

```
PROSPECTING_SOURCES = "kind|name|url[|lane], ..."
        │
        ├── directory       免费：公开的展会/协会/会员名录，定时抓
        ├── licensed_vendor 付费：合同数据（提单/海关），同一个 fetch 协议
        └── mock            演示/测试：确定性合成数据
        │
        ▼  同一条增量协议 fetch(cursor) → FetchResult(records, next_cursor)
   source_runs          游标 + 每次运行的结果（抓了多少、入库多少、为什么被拒）
        │
        ▼
   import_prospects     双键去重 + contact_gaps（有多少条能发信）
        │
        ▼
   score_prospect       逐条打分（模型给理由，分数是代码算的）
        │
        ▼
   send_outreach        四道闸门：人工审批 → 合法依据 → 频次上限 → 分数下限
```

换源只改一行配置，**不改代码、不建第二套系统**。免费源和付费源的区别只在 `kind` 和它带来的 `data_origin`：

| kind | data_origin | 成本 | 有什么 | 没有什么 |
|---|---|---|---|---|
| `directory` | `public_directory` | 0 | 公司名、国家、官网，偶尔有邮箱 | 交易记录、货量、联系人 |
| `licensed_vendor` | `licensed_vendor` | 合同价 | 公司名、HS、金额、港口、日期 | **邮箱、联系人** |
| `mock` | `mock_synthetic` | 0 | 全部字段（假数据） | 真实可用性 |

**关键设计**：`data_origin` 是强制的。一条记录的来源必须能说出来，因为说不出来源的名单恰恰是唯一不能合法发信的名单。这不是字段洁癖，是审计要求。

## 三、定时抓取怎么用（已经能跑）

### 配置

```bash
# 演示：用确定性 mock 源把管道跑通，不碰任何外部站点
PROSPECTING_SOURCES=mock|demo|

# 真实：抓一个公开的展会名录，按页翻
PROSPECTING_SOURCES=directory|canton_fair|https://example.com/exhibitors?page={page}|Shanghai -> Los Angeles
```

格式是 `kind|name|url[|lane]`，逗号分隔多个。`{page}` 是分页占位符——有它才翻页，没有就只抓一页然后标记 `exhausted`。

### 跑

```bash
python -m worker.scheduler          # 常驻：每 15 秒轮询，到期的源才抓
python -m worker.scheduler --once   # 单次：给 cron / systemd timer 用
```

### 看

```bash
curl -s localhost:8100/api/v1/sources/runs | python -m json.tool
```

每次运行留下一条记录：`cursor_before` → `cursor_after`、`fetched`、`accepted`、`rejected`、`note`、`error`。

`note` 是这里最重要的字段，它回答「**这一页为什么是 0 条**」：

- `page 0 via table (42 rows)` —— 正常，解析到 42 行
- `page 0 via links (0 rows)` —— 页面结构变了，表格解析失败，退化到链接也没抓到
- `HTTP 403` / `robots.txt disallows ...` —— 被拦住了

没有这个字段，一个「页面改版导致解析失效」的故障看起来和「这个名录本来就空」一模一样。

### 三条硬约束（写在代码里，不是写在文档里）

1. **robots.txt 强制检查**。拒绝就抛 `SourceFetchError`，不抓。
2. **读不到 robots.txt 就失败关闭**。`robots.txt` 404 视为允许（RFC 9309），但 DNS 失败、超时、5xx 一律视为「未获授权」。因为「我没查到」不等于「我可以」。
3. **不抓海关数据**。中国海关数据是授权制，抓数据商的门户是违约，不是违反 robots.txt。付费路径只有一条：签合同。

这三条在 `tests/test_sourcing.py` 里各有测试，其中 robots 的两条是**能失败的测试**——把检查删掉，测试立刻红。

### 一个限制，先说清楚

抓取是**纯 HTML 解析**，不执行 JavaScript。如果名录是前端渲染的（React/Vue 单页应用，列表在接口返回后才画出来），HTML 里根本没有公司名，`note` 会报 `links (0 rows)` 或 `table (0 rows)`。

这不是 bug，是边界。两条出路：

- 找到页面背后的 JSON 接口，把 `url` 直接指向它（最省事，很多名录的接口就是 `?page=N&format=json`）；
- 上 headless 浏览器（Playwright）。代价是重、慢、容易被反爬，**不建议在验证阶段做**。

先看 `note`，再决定要不要为这个源上浏览器。多数情况下换一个源比上浏览器便宜。

## 四、深度挖掘：从公司名到邮箱（当前最大的缺口）

现状要说清楚：**`enrich_prospect` 还是 mock 的**。系统会诚实报告「这 40 家全都没有邮箱」（`contact_gaps`），但不会去帮你找。

这是对的顺序——先诚实报告，再谈自动补全。否则你会在发信那一刻才发现名单是死的。

要补的三步，按投入产出排序：

### 第一步：官网邮箱发现（低成本，可自动化）

输入是已有的 `website` 字段。做法：

1. 抓首页，找 `mailto:`；
2. 抓 `/contact`、`/about`、`/contact-us` 等常见路径；
3. 从页面文本里正则提取邮箱（注意排除 `example.com`、图片文件名、`noreply@`）。

合规边界和名录抓取完全一样：**只抓公开页面、遵守 robots.txt、限速、带可识别 UA**。抓到的是企业在自己官网上公开的业务邮箱，这是最干净的来源。

风险：命中率低（很多站是表单，没有 mailto），且抓到的多是 `info@` 而非具体负责人。所以它能把 `emailable` 从 0% 提到 20–40%，但到不了 100%。

### 第二步：人工补关键客户（高成本，但只对高分名单做）

不要对 200 家全做。先打分，只对 `score ≥ 70` 的前 20 家人工补。每家 3–5 分钟：官网、LinkedIn、展会名片、企查查。

这一步的产出要回写到 `contact_name` / `contact_title` / `email`，否则下次又要重做。

### 第三步：买联系方式（量大之后才划算）

Apollo / ZoomInfo / 企查查 API 之类。注意两件事：

- 它们的邮箱准确率在 60–80%，**必须验证**（SMTP 探活或第三方验证），否则退信率会毁掉你的发件域名；
- 买来的邮箱**不改变合法依据**。仍然需要 `legitimate_interest_reviewed` 或 `opt_in` 才能发第一封。

## 五、跨行业复用：把「货代」变成配置，而不是复制代码

你说「做一个别的行业类似的搜的工具，模仿来」。**正确的做法不是复制一份代码，是把行业抽成配置。**

现在 `industry` 只是一个打分用的关键词（`app/agents/runtime.py`）。要复用到别的行业，需要把它升级成「行业画像」：

```python
IndustryProfile(
    name='货代-中国出口',
    lane='Shanghai -> Los Angeles',
    # 中英文都要有：只写英文会让中文公司名低 25 分（已踩过，见 MEMORY.md）
    keywords_zh=['机械', '家电', '家具', '纺织'],
    keywords_en=['machinery', 'appliance', 'furniture', 'textile'],
    # 谁不是客户：同行、货代、报关行
    negative_keywords=['freight forwarder', 'logistics', '报关', '货代'],
    # 什么算「有货」：没有这些字段的记录只能算弱信号
    signal_fields=['hs_code', 'amount', 'est_volume_teu'],
    # 找谁：采购/物流/供应链负责人
    title_keywords=['采购', '物流', '供应链', 'purchasing', 'logistics', 'supply chain'],
)
```

换一个 `IndustryProfile`，同一套「发现 → 去重 → 打分 → 触达」就跑另一个行业。**代码零改动，只换 profile。**

这条路的额外好处：它逼你把「为什么这家是客户」写下来。现在这个判断散在 prompt 和启发式里，说不清楚；写成 profile 之后，它变成可评审、可测试、可版本化的东西。

**诚实说明**：这个抽象**还没做**。现在只有关键词打分。上面是形状，不是现状。

## 六、推进顺序（带判定标准）

顺序的原则：**每一步都要能得出「继续 / 停止」的结论**，否则就是自我感动。

### 阶段 0：把管道跑通（已完成）

用 `mock` 源跑 `worker.scheduler --once`，确认 `source_runs` 里有记录、游标在推进、`contact_gaps` 有数字。

判定：连跑三次，`cursor_before` 依次是 `None → 1 → 2`，**并且每页 `accepted` 等于 `fetched`**。

第二个条件不是废话。mock 生成器早期只有 72 种公司名组合，50 条一页会自己撞 13 次，导入报 `accepted: 37`——看起来像「去重抓到了 13 条真重复」，实际是生成器在重复。合成数据如果自带重复，你就分不清「去重在工作」和「数据是假的」。现在生成器按槽位唯一分配，这条断言才能当信号用。

如果 `cursor_before` 不推进，管道是坏的；如果 `accepted < fetched`，先怀疑生成器或去重，别急着怀疑源。

### 阶段 1：接一个真实免费源（1–2 周）

选一个**和你目标行业直接相关**的公开名录：展会参展商名单、行业协会会员名单、B2B 目录。

配置一行，跑两周，每天一页。

判定：**抓 200 家，`emailable` 占比 ≥ 30%**。
- 低于 30% → 这个名录选错了，或者需要先做「官网邮箱发现」（第四节第一步）。
- 不要在这个数字上自欺：`accepted: 200, emailable: 0` 不是成功，是买了一份不能用名单。

### 阶段 2：证明 ICP（2–4 周，最关键）

对前 50–100 家打分，人工复核高分项，发第一封。

判定：**发 100 封，回复 ≥ 5 封（5%）**。

- ≥ 5% → ICP 对了，可以加钱买数据。
- < 3% → **不要买数据**。问题在 ICP 或话术，买更多名单只会更快地烧掉发件域名。
- 回复但都不报价 → 话术问题，不是数据问题。

这个判定是整个路线图的核心。它把「要不要花 20–40 万」变成一个可以实测的问题，而不是一个感觉问题。

### 阶段 3：补联系方式（和阶段 2 并行）

先人工补高分项，再考虑自动化。判定：**人工补 20 家，平均耗时 ≤ 5 分钟/家**。超过就说明该做工具了。

### 阶段 4：买付费数据（只有阶段 2 通过才做）

按 `DATA_SOURCING_CN.md` 的顺序：先中国出口模块，Panjiva 最后。买之前用 `licensed_vendor` 的 `data_as_of` 字段确认「厂商说的更新频率」是不是真的。

### 阶段 5：抽 `IndustryProfile`，复用

只有当阶段 2 在一个行业跑通、且你确实要拓第二个行业时才做。提前做就是给不存在的需求写抽象。

## 七、还没做的（诚实清单）

| 项 | 影响 | 现状 |
|---|---|---|
| 官网邮箱发现 | `emailable` 只能靠名录自带 | `enrich_prospect` 仍是 mock |
| `IndustryProfile` 抽象 | 跨行业要改代码 | 只有关键词打分 |
| `age_days` 参与排序 | 旧名单和新名单同分 | 字段可见，不衰减 |
| 渠道归因 | 不知道哪条路来的客户 | 无 |
| 真并发锁 | 多副本会重复抓/重复发 | 只有单进程 best-effort 保护 |
| 跨厂商实体消解 | 同一公司拼写不同会重复 | 只有名称归一化 |

前两项是这一轮之后最该做的。第三项在 `ACQUISITION_PLAYBOOK.md` 里已经记了一次，这里再记一次：**名单新鲜度可见但不参与排序**，意味着一个 18 个月前的名单和一个上周的名单得分一样，这是个会误导人的设计。
